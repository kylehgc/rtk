# Fork releases use their own tag namespace and restart at 0.1.0

The fork publishes releases so people who find it can install a working binary, which means its tags share a clone with upstream's — 79 `v*` tags and a live `dev-*-rc.*` series are already fetched into this repo. Publishing `v0.45.0` from the fork while upstream publishes its own `v0.45.0` would put two different commits behind one tag name in repos that fetch from both, so **every fork tag carries a `fork-` prefix**: `fork-vX.Y.Z` for stable, `fork-dev-X.Y.Z-rc.N` for the per-push RC track.

Fork versions **restart at 0.1.0** rather than continuing upstream's numbering. Continuing it looked friendlier and is a trap: release-please reads the manifest on `master`, which sat at `0.43.0`, so the fork's first release would have been `fork-v0.44.0` — a number that reads *older* than upstream's `v0.44.1` while actually containing upstream's develop through 0.44.1 plus the fork's own commits. Tracking upstream's number properly would mean hand-reseeding the manifest after every sync, and forgetting once publishes a wrong number permanently. A number that cannot be compared to upstream's cannot lie about it; **the upstream base is stated in the release notes**, where it can be said precisely.

Consequence: `release-please-config.json` and `.release-please-manifest.json` diverge from upstream on `master` only, which makes them Fork Infrastructure (see CONTEXT.md). They are seeded on `master` directly, after the first `develop → master` merge, so `develop` stays byte-identical to upstream and syncs never touch them.
